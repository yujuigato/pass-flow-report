流程架構

Phase 1 — 撈取與認定（21.3 萬列 → 3.7 萬張）
CRM 線索主表加客戶、代碼、員工對照；PASS 日期為有效 8 碼日期才算 PASS 單，只有 Call 紀錄者不納入
Phase 2 — 清理（填充值／問候語／轉介套語／補充說明拆欄）
去換行與空白、清掉無資訊填充值、去掉「Dear」與致謝、轉介套語標記、補充說明依範本拆成 11 個固定欄位
Phase 3 — PASS 類型與狀態分類（24 類，規則不呼叫 LLM）
兩段判斷：內文「此為 XX」（約 29%）→ 前 60 字線索來源（約 71%）；狀態分為已 PASS／未達標準／其他
Phase 4 — LLM：AI 業務摘要 ＋ L1–L7 深度標籤
每張單一次 LLM 呼叫，schema 與日報 Phase 2 對齊；以完整內容雜湊快取，重跑只呼叫新內容
Phase 5 — 法人五階段彙整（S1 PASS → S5 成交）
每張單以「下一張 PASS 或 180 天」為時間窗，串接日報、商機、成交、看板，再彙總到法人；階段彼此獨立不串成一條龍

Phase 1 — 撈取與認定

  • Step 1
    主表撈取
    CRM 線索主表 LEFT JOIN 客戶主檔、代碼對照（工作狀態／客戶來源／PASS 來源）、員工主檔（PASS 窗口、SP、二次 PASS 人員）
    結果：約 21.3 萬列原始紀錄
  • Step 2
    PASS 單認定
    PASS 日期為有效 8 碼日期，範圍 2010-01-01 到執行當天；只有 Call、沒有 PASS 日期的紀錄不納入
    結果：約 3.7 萬張 PASS 單
  • Step 3
    時間窗
    時間窗截止 = MIN(同客戶下一張 PASS 日期, PASS 日期 + 180 天)；之後所有後續動作只看這個區間
    避免把下一張單的事件算到上一張
  • Step 4
    四段後續動作
    日報（事業＋數科，取最早與最新各一筆並計筆數）／商機（取窗內最早）／成交訂單（取窗內最早一張）／機會看板（取最新）
    SDR 與行銷部門建立的紀錄不算「PASS 後業務接觸」

時間窗參數

WINDOW_DAYS       = 180
SHORT_REPASS_DAYS = 30
# 後續動作條件
日期 >= PASS日期  AND  日期 < 時間窗截止

資料來源類別（連線與表名不公開）

  • CRM 線索主表（PASS 單）／客戶主檔
  • CRM 代碼對照表／員工主檔
  • 事業日報、數科日報
  • 事業商機、數科商機
  • 訂單系統（成交）／機會看板

Phase 2 — 清理規則

  • 空白
    空白與換行正規化
    換行、tab、全形空白統一為單一空白（補充說明先保留換行以便依範本拆欄）
  • 填充值
    清掉無資訊內容
    NA、如描述、未定等；「無」「暫無」只在「競爭」欄保留，其餘欄視為空
  • 問候
    去除問候與致謝
    去掉「Dear 某某」與結尾的謝謝；內文以「如下：」收尾而後面沒有內容的 2,007 單，去除該懸空引言
  • 套語
    轉介套語標記
    「懇請／煩請指派規劃師聯繫」是電銷交接的固定收尾
    12,786 單含此套語；拿掉後沒有實質內容的 69 單改標「待規劃師聯繫」
  • 拆欄
    補充說明依範本拆成固定欄位
    規模／現況／需求／使用人數／時程／預算／競爭／決策者／下一步預計行動／預計 Demo 方案／業務回饋；範本外自由文字放「補充備註」
  • 合併
    兩處都有填時合併
    需求、現況、使用人數、時程、競爭在主表與補充說明都有值，用「；」合併，相同或包含者不重複
  • 去重
    重複 PASS 單標記
    同客戶 7 天內、內容涵蓋度 ≥ 80%（3-gram）視為重複，標記「重複於單號」
    結果：246 張被標為重複
  • 再 PASS
    短期再次 PASS
    同客戶 30 天內才視為連續，更久之後各自獨立
    結果：約 1,300 張
備註：2025 年之後的單，補充說明幾乎是空的（新系統不再使用該欄），固定架構欄位以主表欄位為主。

Phase 3 — PASS 類型與狀態分類（規則，不呼叫 LLM）

  • 段 1
    內文開頭有「此為 XX」（約 29%，1,700 多種寫法）
    依 XX 歸成固定類別：待確認商機、Callin／Callout PASS 單、補開立、二次 PASS、單位轉、客服／EGO 轉、專案／活動支援、行銷高機會名單、歷史 PASS 客戶…
  • 段 2
    沒有「此為」（約 71%）
    看內文前 60 字的線索來源或用語：官網／E化單、0800／總機、官方 LINE、客戶主動來電、名單／私田追蹤、準 C1、業務拜訪回報…
    只述「有系統評估需求」者為「僅述系統需求」；都不符合為「未標示」（約 7.5%）

Phase 4 — LLM：AI 業務摘要與 L1–L7 深度標籤

工程設計

  • 快取：內容沒變不重打，失敗不寫快取
  • 平行化：執行緒池＋每分鐘請求上限
  • 歸一化：自由文字欄位做歸一化
  • L7_stage：結果為「進行中」才細分

Phase 5 — 法人五階段彙整（S1–S5）

一家公司一列，五段各自彙整，階段之間不串接成一條龍：各階段彼此獨立，沒發生就留空或為 0，所以商機、成交日期可能早於業務接手日期。

階段主要欄位算法
S1 PASS 建立首次／最近 PASS 日期、累計／近兩年／近一年單數、SDR／MDR 單數、最近等級／狀態／需求／困擾／時程、等級與五大類分布該公司所有 PASS 單
S2 派送處理看板單數、最近看板狀態、二次 PASS 單數與日期有機會看板或二次 PASS 的單
S3 業務接手已接手單數、首次／最近接手日期與接手人、中位距 PASS 天數接手日期＝各單 PASS 後第一筆業務日報
S4 商機有商機單數、首筆／最近商機日期、類型、狀態、等級各單時間窗內最早一筆商機
S5 成交有成交單數、首次／最近成交日期、各單首張成交金額合計各單時間窗內最早一張成交訂單

下一步與接手人

下一步取時間窗內最早發生的動作（二次 PASS、轉入業務私田、商機、成交、短期再次 PASS），其他動作並列在「後續動作」。接手人為首次業務日報的建立人，與 PASS 窗口、指定 SP 及內文載明的 SP 比對，得出「接手人是否為 PASS 指定」（為「否」不一定有誤，可能轉給同事或先由電銷聯繫）。

表一列代表寫入方式

單的維度：pass_detail（59 欄）

  • 識別與日期：潛客代號、PASS 單號、PASS 日期、年月
  • 分類：負責類型、PASS 類型、來源、五大類、等級、狀態
  • 客戶資訊固定架構 15 欄（規模…業務回饋）
  • 指派與建立、PASS 內容、AI 業務摘要
  • L1–L7 共 21 欄＋L7_stage

法人的維度：pass_company_summary（69 欄）

  • S1–S5 五段彙整，每單後續以時間窗判斷再彙總
  • 最近一張單的 L1–L7 標籤
  • 單層級的後續動作不寫入資料庫
  • 月度表只保留近兩年，更長期間對 pass_detail 做 GROUP BY

歷史快照規則

比對時不看「快照日期」「寫入時間」；公司第一次出現，或內容與歷史表最新一筆不同，才附加一列。同一天重跑、沒有變動不會重複附加。欄位改版時保留舊列重建。

查詢範例

-- 某家公司所有過往 PASS 單（新到舊），含深度標籤
SELECT PASS日期, 等級, 狀態分類, 需求, 困擾, AI業務摘要,
       L6_current_temp, L6_direction, L7_outcome_type, L7_stage, L7_next_step
FROM pass_detail
WHERE 潛客代號 = N'請填潛客代號'
ORDER BY PASS日期 DESC;

-- 月度統計（取代全歷史月度表）
SELECT 潛客代號, 年月, COUNT(*) AS 當月PASS單數
FROM pass_detail
GROUP BY 潛客代號, 年月;

資料品質與使用限制

  • 時間窗
    後續動作設上限
    原型 SQL 無上限，容易把多年後的成交算回第一張單；改為「下一張 PASS 或 180 天」
  • 階段獨立
    不排成一條龍
    S1–S5 各自獨立，沒發生就留空；避免因資料缺漏而編造不存在的轉換順序
  • 快取
    LLM 結果依內容雜湊快取
    重跑 4 種新內容只需 13 秒；失敗的內容不寫快取，下次自動補
  • 歷史
    歷史快照有變才附加
    重跑與同日重複寫入不會讓歷史表膨脹

已知限制

  • 資料範圍是全公司，不只單一產業。
  • 只有 Call 紀錄、沒有 PASS 日期的資料不納入。
  • 當天剛建立的單，後續欄位為空屬正常。
  • 業務私田的接手時間只能參考日報；歸屬表只有現任歸屬，沒有歷史。
  • 9 大問題的確切欄位尚未確認，目前沒有計算完整度。
  • 重複執行寫入：前三張重建，歷史表再附加一份快照（有變才附加）。
