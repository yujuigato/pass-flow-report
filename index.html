Background

這個系統在解決什麼問題？

PASS 單是電銷判斷客戶有需求後轉給業務的線索單。單據寫在 CRM 的自由文字裡，而 PASS 之後發生什麼事，又散落在日報、商機、訂單三個系統，沒有人能一次看完整條路。

😣 過去的痛點

  • 21 萬筆線索紀錄裡，只有約 3.7 萬筆帶有有效 PASS 日期，其餘多為只有 Call 的紀錄，需先篩出
  • PASS 類型與來源只寫在內文開頭，光「此為…」就有 1,700 多種寫法，無法統計
  • 內容常常很短甚至空白，真正的需求、困擾填在別的欄位；還夾雜問候語與「請指派規劃師聯繫」等套語
  • PASS 之後有沒有被接手、有沒有商機、有沒有成交，要跨日報、商機、訂單三個系統人工比對
  • 同一客戶重複開單，單據之間誰接誰，分不清楚

✅ 系統如何解決

  • 以 PASS 日期認定真正的單，並清理空白、填充值、問候語與套語
  • 兩段規則把 24 種類型與狀態標準化，不需呼叫 LLM、結果可解釋
  • LLM 對每張單產出 AI 業務摘要與 L1–L7 標籤，把文字變成可統計的欄位
  • 為每張單設定時間窗，串起日報接手、商機、成交、看板
  • 彙整成「單」「法人」「月度」「歷史」四張表，一個查詢就能看完整歷程
How It Works

系統如何運作？

六個階段由原始線索一路處理到分析表，每一步都有明確的輸入、輸出與判斷標準。

💡 PASS 單在業務流程中的位置

電銷依負責區分：SDR 處理顯性需求、MDR 處理隱轉顯需求；對客戶做 9 大問題判斷，回答 Y 的進入電銷私田，開立 PASS 單並分五大類；PASS 後轉入業務私田，由業務接手經營。系統就是把這條路徑上的資料還原出來：

SDR／MDR → PASS 來源分類
五大類 → 需求分類碼（ERP／ERPII、行業管議、OT、infra、敏態新生意）
9 大問題 → 需求、人數、現況、困擾、時程、競爭等欄位
轉入業務私田 → 以 PASS 後第一筆業務日報作為接手時間

Phase 1：撈取與認定

CRM 線索主表加上客戶、代碼、員工對照；PASS 日期為有效 8 碼日期才算 PASS 單，沒有有效 PASS 日期的紀錄不納入。

21.3 萬筆原始紀錄 → 37,152 張 PASS 單。每張單的「時間窗」＝ 同客戶下一張 PASS 與 PASS 日期＋180 天，取較早者，後續動作只看這個區間
2

Phase 2：清理與固定架構拆欄

統一空白換行、清掉無資訊填充值、去掉問候與致謝、標記轉介套語，並把補充說明依範本拆成 11 個固定欄位。

規模／現況／需求／使用人數／時程／預算／競爭／決策者／下一步預計行動／預計 Demo 方案／業務回饋；主表與補充說明都有填時用「；」合併
3

Phase 3：PASS 類型與狀態分類（規則）

第一段看內文開頭「此為 XX」（約 29%）；第二段看前 60 字的線索來源與用語（約 71%）。

客戶主動來電／來信、官網／E化單留言、待確認商機、Callin／Callout、0800／總機、官方 LINE、二次 PASS、專案／活動支援…共 24 類；狀態分為已 PASS／未達標準／其他
4

Phase 4：AI 業務摘要與 L1–L7 標籤

先組出「完整內容摘要」（結構化欄位＋原始描述），再對每張單呼叫一次 LLM，產出一段話摘要與七層標籤。schema 與日報 Phase 2 完全對齊。

L1 起因／阻礙 → L2 角色壓力 → L3 戰略目標 → L4 產業議題 → L5 問項精煉 → L6 動態溫度 → L7 實戰對策（進行中者再細分 L7_stage）
5

Phase 5：法人五階段彙整

每張單的後續（日報接手、商機、成交、看板、二次 PASS）依時間窗串接，再彙總到法人，分成 S1 PASS、S2 派送、S3 接手、S4 商機、S5 成交。

五段各自獨立、不串成一條龍：沒發生就留空或為 0，所以商機或成交日期可能早於接手日期，如實呈現資料
6

寫入：四張分析表

單、法人、月度三張每次重建，法人歷史表只在內容有變時附加一列快照。

預設只輸出本機預覽檔，確認後才加參數寫入資料庫
Engineering Challenges

解決了哪些技術難題？

Challenge 1

1,700 多種寫法的 PASS 類型

類型只寫在內文開頭，業務各寫各的；全丟給 LLM 成本高，結果也難以解釋與重現。

↓ 解決方案

人工檢視實際寫法後訂定兩段規則（「此為 XX」→ 前 60 字線索），由上到下先符合者為準。零 LLM 成本、結果可追溯，未標示僅約 7.5%

Challenge 2

後續事件該算給哪一張單？

同一客戶會開多張單，若不設界線，多年後的成交會被算回第一張單，轉換率被嚴重高估。

↓ 解決方案

每張單設時間窗：同客戶下一張 PASS 與 PASS＋180 天取較早者；SDR 與行銷部門建立的紀錄不算 PASS 後業務接觸

Challenge 3

內容太短、太雜，LLM 容易亂編

PASS 內容常常只有一行，甚至只剩問候語與「請指派規劃師聯繫」；餵給 LLM 會得到無依據的標籤。

↓ 解決方案

先清掉問候與套語（12,786 單含套語、69 單拿掉後無實質內容，改標「待規劃師聯繫」），再把散在各欄位的需求、困擾組成完整內容摘要；內容過短不萃取，沒有證據就留空

Challenge 4

3.7 萬次 LLM 呼叫的成本與重跑

每次重跑全部重打，費用與時間都不可接受；呼叫失敗也不能讓整批作廢。

↓ 解決方案

以完整內容雜湊為 key 的快取＋20 個並行 Worker 與每分鐘上限；失敗不寫快取。11/19 重跑時 37,031 種內容中只有 4 種是新的，約 13 秒完成

Challenge 5

資料沒有「轉移時間」

CRM 沒記錄 PASS 何時轉到業務手上，歸屬表也只有現任歸屬，無法直接算「多久被接手」。

↓ 解決方案

以 PASS 後第一筆業務日報作為接手時間，並與 PASS 指定窗口、指定 SP 及內文載明的 SP 比對，判斷接手人是否為指定；結果標明這是推算值

Challenge 6

重複單與再次 PASS 干擾統計

同客戶短時間內重複開單，會讓單數、轉換率失真，也分不清是重複還是真的再次 PASS。

↓ 解決方案

同客戶 7 天內、內容涵蓋度 ≥ 80%（3-gram）標記為重複（246 張）；30 天內才視為短期再次 PASS 並互相連結（約 1,300 張）

Challenge 7

追蹤法人狀態的變化

公司彙整表每次重建只剩「現在」，看不出什麼時候從無商機變成有商機。

↓ 解決方案

歷史表只在公司第一次出現或內容與最新快照不同時附加一列；比對不含快照日期與寫入時間，同日重跑不會重複堆積

Challenge 8

缺資料時不編造

9 大問題的確切欄位尚未確認，階段之間的時間先後也不一定成立。

↓ 解決方案

五個階段各自獨立彙整、缺值留空；下一步只取時間窗內最早發生的動作，其餘並列為後續動作；文件明列已知限制
